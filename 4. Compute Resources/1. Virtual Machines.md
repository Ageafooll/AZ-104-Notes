
**Azure VMs** are **IaaS** compute resources which you have total control over the configuration and OS and can install anything you need without having to purchase physical hardware. It also provides services and extensions that provides monitor, secure, and manage updates and patches to OS.

There are several things you should consider when creating a VM:
- **The network** - You choose a **subnet** in a **virtual network (VNet)** to put the **VNIC**s attached to the VM in. You think about the IP address space and private connectivity you'll need with other services with VM.
- **Virtual Netwrok Interface Card (VNIC)** - Choosing if we will use public ip addresses for the VM or **Network Security Groups (NSGs)** to control flow of traffic thourgh VNICs and subnets. (VNIC should be in the same region with the VNet it is attached to).
- **VM name** - You can't change VMs name after deployment.
- **Location** - You choose a geographic region to deploy the VM in. You may choose it as close as to customers or in a regulatory boundary.
- **Size** - VM size options allows you to select appropriate mix of **compute**, **memory** and **storage**(IOPS, disk amount) according to your goal. A size can be general purpose, compute, memory, storage optimized, GPU or High performance compute.
  You can change the size of a VM if you want, if you **deallocate** it you can change it to any size you want but if you don't you can change it only to available options. The VM will reboot after the change.
- **Storage** - VMs have at least two **virtual hard disks (VHDs)**. One stores the OS the second is temporary storage. You may add more data disks to store persistent data. Might be Ultra disks, Premium and Standard SSDs and Standard HDDs.
- **Operating System** - You may have to pay for licenses. You can search **Azure Marketplace** for more sophisticated images that include software tools in image too. You can create your own image to create your VMs too, you can use **Azure Compute Gallery** to manage multiple images and replicate them to the regions.

To deploy a VM you can use the **portal**, **Powershell**, **CLI**, **REST API** or **Client SDK**s.

You can configure **Encryption at host** for VMs. More than regular SSE, it encrypts data at the compute host hardware too like temp disks and caches, and flows encrypted over the network. You must register the feature in subscription with 
```
az feature register --namespace Microsoft.Compute --name EncryptionAtHost
```

**VM extionsions** are small applications that lets you configure and automate tasks on VMs after initial deployment. They are directly connected to **Automation Services**. You may run scripts (Automation Account runbook), monitor health (Azure Monitor Agent), manage configurations (PowerShell Desired State Configuration), Azure Backup VM extension etc.

You may configure up to three **Availability Zones** for your VMs for resiliency or **Virtual machine scale sets**(talk about it later). Azure storage redundancy takes care of storing multiple copies of your disk data (ZRS, GRS etc.).

To handle regional failovers we can replicate our data and infrastructure almost in real time with **Azure Site Recovery**. It works for both on-premises and cloud resources. It can be simple or complex depending on your scenario like using Automation runbooks, manual intervention steps etc.

For backups you may use **Azure Backup**. It is used for Files and folders on Windows, Linux OS, Application-aware snapshots etc. for both on-premises and cloud resources. It is backup as a service it takes care of storage and scaling automatically.

You can move VMs between rgs and subscriptions by selecting it and all its dependent resources and click move. It remains powered on and ip addresses stay intact. Or between regions with Resource Mover which replicates it to another region and shuts down when you click move and target is spinned up. Ip address of it may change.
You may check some restrictions from learn.microsoft -> Azure Resource Manager -> How to -> Move Resources -> Azure services.
