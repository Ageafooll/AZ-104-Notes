
An **App Service plan** defines a set of compute resources(server farm) for a web, mobile backend, API application to run. Multiple applications can run in one app service plan.

You consider these when creating one:
- **Region** - You can not change it later. 
- **Operating System** - You can not change this later either.
- **Pricing Tier** - Can scale up or down to change later
- **Zone redundancy** 

**Pricing tier** determines what **App Service** features you get and how much you pay for the plan. It determines how much vCPU, memory, storage you will have for one instance of underlying VMs and how many instances you can **scale** up to and some features like custom domain, auto scale, staging(deployment) slots etc.

You can see which plan has which features from learn.microsoft -> Management and Governance -> resource manager -> subscription and service limits.

They are grouped into three categories:
- **Shared compute** - Free. apps run on the same Azure VM as other App Service apps including apps of other customers. allocates cpu to each app and can't scale, used for development and testing
- **Dedicated compute** - Basic, Standard, Premium. run on dedicated Azure VMs. apps in same app service plan have the same compute resources. higher the tier the more instances available to scale out. for production and new deployments
- **Isolated** - Isolated, dedicated Azure VMs on dedicated virtual networks. maximum scale out capabilities. for new workloads

Your options when you want to **scale out/in** are **Manual** or **Automatic** or **Rule Based**.

For **Automatic scaling**(Elastic sacling) you don't configure rules. Azure manages the scaling based on HTTP traffic with warmed, always-ready instances. Available for some Premium tiers.

For **Rule Based**(Autoscale) you configure autoscale profiles and rules based on **Metric** or **Time-based**.

You specify minimum/maximum instance counts and a default instance count for when the metrics aren't available. And the start/end dates for when that profile is considered for autoscale, outside of that interval it'll fallback to default profile.

For metric you can configure average CPU percantage, queue length for an interval etc.. how many instances to add or remove and cooldown after scaling:

You can also configure notifications after a rule is triggered that can send emails or make calls to a webhook.

Azure automatically handles the load balancing after scaling. Internal load balaning configurations are handled for you.
