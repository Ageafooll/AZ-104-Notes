
While virtual machines virtualizes the hardware, **containers** virtualize the operating system. Here are the comparison to decide which one to use:

| Container                                                                       | Virtual Machine                                                                           |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Lightweight isolation.                                                          | Complete isolation from the host OS and other VMs. Strong security boundary.              |
| User mode portion of OS. just needed services used, fewer system resources used | Runs a complete OS including kernel, more system resources used.                          |
| Azure Disks used for local storage or Azure Files (SMB shares) for shared       | Virtual hard disk(VHD) for local storage or SMB file share for shared by multiple servers |
| If fails, orchestrator rapidly creates another one.                             | If fails, it can fail over to another server and OS restarts.                             |

**Azure Container Registry (ACR)** is a managed private container registry PaaS. It's premium SKU has several features like geo-replication, artifact streaming, image security and ACR tasks which enables us to automate image building, testing upon commits or updates to base image improving CI/CD.
You can disable public access with premium SKU and a private endpoint, for access you can use registry admin account(not recommended) or Entra ID with roles (AcrPull etc.).

**Azure Container Instances (ACI)** is the simplest way to run containers in Azure. You can pull an **image** for the container from **ACR** (with managed identity) or docker hub. Size choices are more flexible:

**Container group** is the top-level resource of ACI, it is a collection of containers that share a lifecycle, resources, local network and storage volumes and scheduled on the same host machine. If networking type is private it'll need its own dedicated subnet (Multi container group can't be deployed on portal and must use another method like ARM template or YAML files):
![[Pasted image 20260809135710.png|533]]
It is useful for scenarios like one container serves the web app and another one pulls the latest content from source control. or one container is a monitoring container.

**Azure Container Apps (ACA)** is a **serverless** platform allows you to less care about the infrastructure while running containerized apps. It is built on Azure Kubernetes Service (AKS) and provides automatic scaling on resources based on HTTP traffic, CPU load, any KEDA-supported scaler etc. You don't manage kubernetes itself it is abstracted. It supports **multiple revision mode** which allows us to splits traffic between multiple versions of our app. It also has health probes (container lifecycle probes).
It is useful for apps that span many microservices, kubernetes-style apps.

They run in a **Container Apps Environment** which is a boundary for our containers with shared network and logging. 
**Workload profiles** determines the type, size and scale instances available for the apps inside the environment it might be **Consumption** (Pay as you use like Azure Functions, scale to zero) or **Dedicated** (pre-provisioned infrastructure, you configure **infrastructure scaling** for nodes, supports UDR, NAT GW, private endpoints unlike consumption).
By default **ACA** manages the VNet for you but you usually bring your own VNet for your production and you need a dedicated subnet for the container apps environment (at least /27 for dedicated and /23 for consumption). When you choose internal it'll be given a load balancer with private IP.
