
**Azure Files** offers fully managed file shares in the cloud, you can access file shares by using **Server Message Block (SMB)**, **Network File System (NFS)** and HTTP protocols. It is useful for lift and shift scenarios, shared application settings, storing tools and utilities that are needed for administering resources.

Here are some comparisons between Azure Files and Blob Storage

| **Azure Files**                                                                         | **Blob Storage**                                                                  |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| provides SMB, NFS, client libraries, REST interface                                     | provides client libraries, REST interface                                         |
| Files here are true directory objects                                                   | Blobs are a flat namespace                                                        |
| Data here is accessed through file shares                                               | Blob data is accessed through a container                                         |
| Ideal to lift and shift applications to cloud that already uses native file system APIs | Ideal for applications that need to support streaming and random-access scenarios |
A file share don't support both SMB and NFS at the same time. But different file shares in the same storage account can support one each.

Azure Files support different access tiers like blobs. Two storage tiers are premium (SSD-backed) and standard (HDD-backed). Top down access tiers are **Premium**(pay for capacity reserved), **Transaction Optimized**, **Hot**, **Cool**. (you can't change from standard to premium vice versa once the account is created)

For accessing Azure Files if you are using SMB / Mapped Drives there is two-layer permission. Using Kerberos and authenticating with a identity source for authorization on files is **SMB Identity based access/authentication**.
**Share-Level** controls who can access the file share itself with **RBAC** roles like "Storage File Data SMB Share Contributor".
**File/Directory-Level** enforces granular rwx permissions on specific folders and files with **NTFS ACLs**. You must have a Line of Sight to **Microsoft Entra Kerberos**, **on-premises AD DS** or **Entra Domain Services** to resolve identities. (permissions are edited before by an administrator from properties -> security on files).

**Access key**s and **SAS** bypasses NTFS ACLs.

**Azure Storage Explorer** is a standalone application that lets you work with Azure Storage in multiple accounts and subscriptions.
You need both management and data layer permissions for full access with this. You may use keys for your own subscription or attach storage account or services with SAS for another Azure subscription.

**Azure File Sync** enables you to cache several Azure SMB Files shares on-premises Windows Servers or cloud virtual machines. It centralizes our organizations file shares while keeping flexibility, performance, compatibility of an on-premises file server. The components are like following:

A **cloud endpoint** represents the Azure Files share and acts as a hub.
In a **sync group** you can have only one **cloud endpoint** , you can have multiple **server endpoint**s but only one endpoint per physical server in a group.

You may manage the data from the portal, **Azure CLI/PowerShell**, **Azure Storage Explorer**, **AzCopy**(command-line tool, between storage accounts and regions), **Azure Data Box Disk** (they send you disks and you upload it to disks and send these to them through cargo) or **Azure Import/Export** (Same as data box but you provide the disks).

If we have RBAC Data plane permissions we can manage data from PowerShell like this after logging in:
```
Connect-AzAccount 

Set-AzStorageBlobContent -StorageAccountName "mystorageaccount" -Container "mycontainer" -File "C:\local\report.pdf" -Blob "report.pdf" -UseConnectedAccount
```
Or if we will use a key or a SAS we will set and use the storage context:
```
$storageContext = New-AzStorageContext -StorageAccountName "mystorageaccount" -SasToken $sasToken

Set-AzStorageBlobContent -File "C:\local\report.pdf" -Container "mycontainer" -Blob "report.pdf" -Context $storageContext
```

A bit more advanced command would be like:
```
Get-ChildItem -Path "C:\LocalLogs" -Filter "*.log" | Where-Object { $_.LastWriteTime -gt (Get-Date).Date } | ForEach-Object { Set-AzStorageBlobContent -File $_.FullName -Container "daily-backups" -Blob $_.Name -Context $storageContext }
```

**Azcopy** supports Azure Files, Blobs and Data Lake Storage. To authorize Azcopy you can login to Entra ID with "azcopy login" or use SAS or account keys in the command.
If we were to use SAS and copy contents of a directory to Azure Files it'd be like this (you don't set context like Azure Powershell, it expects full URI):
```
azcopy copy 'C:\myDirectory' 'https://mystorageaccount.file.core.windows.net/myfileshare/myFileShareDirectory?[SAS]' --recursive --preserve-permissions=true --preserve-info=true
```
Or for synchronizing changes in Blobs and already have RBAC permissions it'll be: (--delete-destination deletes files in container if it was deleted from the source):
```
azcopy sync "C:\data\project-files" "https://stpowershelllab123.blob.core.windows.net/projects/" --delete-destination=true
```
