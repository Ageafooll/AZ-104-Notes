
**Azure Policy** is a service that lets you create, assign and manage governance policies that enforce rules and effects over your resources(current and forthcoming) to ensure they stay compliant with your governance standards. It evaluates resources and actions by comparing their properties to business rules. In some cases it can automatically remediate noncompliant resources. The **compliance dashboard** presents environment's overall state.

**Microsoft Cloud Adoption Framework for Azure** offers technical guide for Azure. It helps businesses reach their cloud adoption objectives. Its **Govern** methodology addresses areas such as regulatory compliance, security, operations, cost management, data, resource management etc.

When designing an Azure Policy you should strike a balance between **control and stability** in one area with **speed and results** in other.

You have four levels of management (management groups, subscriptions, resource groups, resources) for applying policies, policies are inherited top down. The **definition location** determines the scope which the initiative or policy can be assigned.

**Azure Resource Manager (ARM)** provides the management layer that lets you create, update and delete resources in Azure.

Azure operations are in two types: **control plane** and **data plane** 

The **control plane** lets you manage resources in your subscription. Azure Policy mostly operates in control plane. ARM manages all control plane operations, all control plane requests goes through ARM. ARM manages functions such as deployment with templates, RBAC(ones in control plane), auditing, monitoring and tagging.

The **data plane** is where the data operations occur, involves direct interaction with the data in resources (doesn't goes through ARM). Service specific access controls (RBAC, ACLs) that manage data plane permissions.

Azure Policy supports managing data plane operations too with services whose resource providers implemented Azure Policy extensions (like Microsoft.Kubernetes.Data)

ARM handles requests in two scenarios **Greenfield** and **Brownfield**

**Greenfield** is when a Azure Policy (policy-first) already exists when request is processed.

**Brownfield** is when resources already exists (resource-first) and you are assigning a new policy to them. Evaluation happens through a compliance scan which runs automatically or manually triggered

RBAC is evaluated before Policies

**Built-in policy** is a type of policy definition that's generated by Azure Resource Providers and available by default. Grouping of them is **built-in initiatives**.

**Custom policy** is written by a user when no built-in maps to our requirements. Grouping of them is **custom initiatives**. Microsoft for Sovereignty uploads some in a github repo. 

**Policy resources** are control plane objects, they have distinct resource provider namespace and resource IDs, there are six types:
- **Definitions** - They describe resource compliance conditions and the effect to take if a condition is met.
- **Initiatives** - AKA policy set, allows you to group several policy definitions to simplify assignment and management because you work with them as a single item. It helps you track compliance for organizational compliance goals or compliance with **regulatory frameworks**(GDPR, KVKK)
- **Assignments** - Defines which resources are evaluated by a policy or initiative. They are assigned to a specific scope in their location. You can define several option aspects like in here: ![[Pasted image 20260728164032.png]]
- **Exemptions** - This exempts a resource hierarchy or resource from the evaluation of policies. They count towards overall compliance (unlike excluded ones). These created after the assignment, two categories exists which are **Mitigated**(intent is met through another method) or **Waiver**(noncompliance is temporarily accepted).
- **Attestations** - It is for **manual policy assignment**s, compliance isn't automatically checked and done by human manually. Attestation is the record or document to change the resource compliance state from "Unknown" to "Compliant" or "Non-Compliant".
- **Remediations** - Is used to bring noncompliant resources into a compliance by a task, with "modify" or "deployIfNotExists" in definition.

You use JSON to create a policy definition. like this example:
```
{
  "displayName": "Allowed locations",
  "description": "This policy enables you to restrict the locations your organization can specify when deploying resources. Use to enforce your geo-compliance requirements. Excludes resource groups, Microsoft.AzureActiveDirectory/b2cDirectories, and resources that use the 'global' region.",
  "policyType": "BuiltIn",
  "mode": "Indexed",
  "metadata": {
    "version": "1.0.0",
    "category": "General"
  },
  "parameters": {
    "listOfAllowedLocations": {
      "type": "Array",
      "metadata": {
        "description": "The list of locations that can be specified when deploying resources.",
        "strongType": "location",
        "displayName": "Allowed locations"
      }
    }
  },
    "policyRule": {
      "if": {
        "allOf": [
          {
            "field": "location",
            "notIn": "[parameters('listOfAllowedLocations')]"
          },
          {
            "field": "location",
            "notEquals": "global"
          },
          {
            "field": "type",
            "notEquals": "Microsoft.AzureActiveDirectory/b2cDirectories"
          }
        ]
      },
      "then": {
        "effect": "deny"
      }
    }
  }
```

Some "effect"s are **deny**(not disabled), **audit**, **deployIfNotExists** etc. you can find more of the definition structure options in "Azure Policy definition" documentation in ms learn.

After a compliance scan, resources can be in these **compliance states**: **Non-Compliant**, **Compliant**, **Error**(about template or evaluation), **Conflicting**, **Protected**, **Exempted Unknown**(manual).

**Enforcement Mode**(enforcementMode) is a property of policy assignment that lets you deactivate the enforcement of certain policy effects, it is good for testing, modes are:
- **Default**(Enabled) - The policy is enforced during creation or update
- **Do Not Enforce**(Disabled) - The policy effect isn't enforced
