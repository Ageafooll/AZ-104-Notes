
**Azure virtual networks** is a logical isolation of the Azure cloud resources, it is an essential component for creating private networks in Azure.
You can use them in many ways like:
- **Creating a dedicated private cloud-only network** - Services and VMs in the VNet can communicate directly and securely.
- **Securely extending our data center with virtual network** - Can build a site-to-site VPNs using IPSEC to create a secure connection between our corporate VPN gateway and Azure.
- **Hybrid cloud scenarios** - Can securely connect cloud-based applications to on-premises systems like mainframes and Unix systems.

**Subnets** allows us to logically divide our VNet. They contain a range of ip addresses that fall within the VNets address space, must be unique within the VNet and shouldn't overlap with other one. 5 addresses are reserved in each subnet 2 for network and broadcast address, 1 for gateway and 2 for DNS.
![[Pasted image 20260811131139.png]]

Some services like **Azure VPN Gateway** or **Bastion** requires their own dedicated subnets. Azure routes network traffic between all subnet in a VNet by default, we can override this to make traffic between subnets to be routed through a **network virtual appliance**.

Normally there is a service that lets resources with private ip addresses to talk to the internet with automatic source NAT, but when you check **enable private subnet** it is disabled and only the ones with a public ip can communicate to the internet.

When we create a **virtual network** we consider using an ip address space that is not already in use in our organization.
![[Pasted image 20260811132104.png|494]]
When planning ip addressing there are two types of addresses:
- **Private IP addresses** - Enables communication within and VNet and on-premises network, we can create private ip addresses for our resource using **VPN Gateway** or **ExpressRoute** to extend our network to Azure.
- **Public IP addresses** - Allows our resources to communicate with internet, we can use it for public-facing services.
![[Pasted image 20260811132528.png|625]]

We can **statically** or **dynamically** assign addresses. Static are best for scenarios like, Dns name resolution, address based security models, TLS/SSL certificates linked to an address etc.

You can create a public ip address resource on demand for attaching it to a resource later.
You should specify the **SKU** which must match the SKU of the Load Balancer it is used and **Tier** which also must match the load balancer tier:
**Cross-region(Gloabal)** load balancer distributes traffic across regional backends. **Regional** distributes it within a virtual network.
![[Pasted image 20260811135230.png|540]]

You associate the **Public IP addresses** on various resources like:
- VMs from vNIC config
- Virtual Network Gateway, NAT Gateway from Gateway IP config
- Public Load Balancer, Application Gateway, Firewall, Route Server from Front-end config
- Bastion host from public ip config

**Private IP addresses** can be assigned dynamically (next available address) or statically assign it to VM vNICs, Internal Load Balancers, Application gateways.
