
**Virtual Network peerings** lets us connect VNets in the same or different regions providing secure communication between resources in the peered networks using Microsofts network backbone.
![[Pasted image 20260814135615.png|500]]

There are some things to consider for peering:
- Peered VNets must have **non-overlapping** IP address spaces.
- If we wan't to change a VNets address range, we should delete the peering first.
- For communicating with internal load balancers thorugh peering, the LBs SKU must be "standard" (basic can't).
- You should explicitly link the **private DNS zone** to both VNets, having a peering doesn't means it'll implicitly do name resolution from the peered VNets linked DNS zone.

![[Pasted image 20260814140423.png]]

You can configure **Azure VPN Gateway** in the peered VNet (usually in a hubs gateway subnet) as a transit point, a peered VNet uses the remote VPN gateway to gain access to other resources (usually on-premises resources).

A peering is uni-directional, so you have to configure a peering both from A to B and B to A. But when you add peering from the portal it'll make you configure both of them at the same place. A peering can be vnet-to-vnet or subnet-to-subnet.
When configuring from VNet A, for some reason the remote peering(B-to-A) config will be upper the local peering(A-to-B) config.

![[Pasted image 20260814141910.png|634]]

There is four key settings by order when configuring a VNet peering (in VNet A to B settings):
- Controls whether traffic flows from VNet A to B (allows genereal communication)
- Controls whether forwarded (non-originating) traffic is accepted from the VNet B (required if B passes traffic through A)
- Enables **gateway transit**, lets the VNet B use A's VPN Gateway or Route Server. (A shares its gateway)
- Enables VNet A to use VNet B's VPN Gateway or route server. (tells A to route crypto/on-prem traffic to B) (you don't need to add UDR for it for A, its subnet automatically learns routes known to Bs gateway)

For instance, if we were to make B use the VPN Gateway in A. 
In A to B we would check 1,2 and 3
In B to A we would check 1,2 and 4

The two peering status conditions are **Initiated** (if reverse link is missing) and **Connected** (if the reverse link exists). Both should be Connected for successfully establishing the peering.

![[Pasted image 20260814144907.png|556]]

VNet peering is nontransative, like if you are planning a **hub-and-spoke** network and peered A and B, B and C, this doesn't means A and C can communicate right away. To address this you use **User-defined route (UDR)**(next module) or **Azure Virtual Network Manager** which manages and automates hub-and-spoke or mesh peering topologies at scale.

**Service chaining** is a networking method that directs traffic from one VNet through a specific sequence of **Network Virtual Applicances(NVA)**(Could be a firewall for inspection) or gateways in a peered network with UDRs. Used in hub-and-spoke topologies we talked about before.
