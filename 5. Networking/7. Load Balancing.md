
**Azure Load Balancer** allows you to evenly distribute incoming traffic across a group of VMs or across instances in a Virtual Machine Scale Set. It operates at **Layer 4**. 

We can deploy it as public or internal (you can't change it once deployed):
- **Public load balancer** - Is used to load balance internet traffic. Uses **public IP address**. And maps the address and the port number of incoming traffic to the private IP and port number of the back-end pool VMs. It can also provide outbound connections for VMs inside the pool.
- **Internal load balancer** - Uses **private IP address** for front-end configuration. Used for cross-premises VNets and multi-tier applications.

It can be deployed with **basic** or **standard** SKU, the SKU of the public IP and Load Balancer must match. Standard SKU is secure by default so the traffic to VMs must be explicitly allowed by an NSG to work (allowing inbound TCP 443 etc.). Load Balancers sits at the edge so the destination of packet gets translated before the NSGs are evaluated.

It can be zone redundant or zonal. (LB itself being zone redundant doesn't means the back-end pool is zone redundant too).

Several elements of load balancer work together for this:

**Front-end IP** can be public or private. you can't assign a public IP to one which created as a internal vise versa. Multiple front-end IPs can have different load balancer rules. Same front-end IP can have different configurations for different ports too. (like different load balancer rules for port 80 and 443) You can also use multiple at a time so if simultaneous connections exceeds the all port numbers so you can have extra 45k connections.

**Load Balancer rules** determines how traffic is distributed to a back-end pool from a front-end IP and port. **Session persistence** A.K.A session affinity under this provides stickiness only within a transport session. It uses two, three or five-tuple hash to route to same back-end instances you can configure it with following options. **None** (default) any healthy VM can handle the request (5-tuple), **Client IP and protocol** (3-tuple) uses source/dest IP and protocol, **Client IP** (2-tuple) uses source and dest IP. Idle timeout is how long a session will stay open in inactivity.

**Back-end pool** is group of VMs or instances in a VMSS that responds to incoming requests. LB automatically reconfigures itself to redistribute the load when the instances in the back-end pool scales out/in. LB and back-end pool resources must reside in the same VNet (peerings won't work, but can be in different subnet in the same VNet), if VM has public IP the SKU must match with load balancer SKU (VM can be stopped(allocated/deallocated), and still exist in the backend pool, the traffic just won't be forwarded to it).

**Health probes** are used to determine the health status of the instances in the back-end pool. We can configure the thresholds. If it fails LB will stop sending new connections to the unhealthy instances. We can configure different probe types like **TCP** custom probe, **HTTP** or **HTTPS** custom probe (Health probes are still sent even when the VM is marked as unhealthy in case it comes back).

**Inbound NAT rules** allows you to manage a specific instance in a pool (SSH, RDP...) with a NAT rule. (not needed for load balancing the regular traffic). (Its better to prefer using a Bastion over this).

**Outbound NAT rules** uses source network address translation (SNAT) and allows the instances in the pool to communicate outbound to the internet or other public endpoints. (not needed for load balancing the regular traffic)

**Application Gateway** load balances HTTP traffic across web servers. It works up to layer 7 that it supports WebSocket, HTTPS protocols too load balancing based on host names and paths. Has the features that load balancer has (health probes, internal/public) plus these:

It used **cookie based affinity** instead of IP based.

It also can work as a **web application firewall (WAF)** with Core Rule Sets (CRS) defined by OWASP. Also supports **TLS/SSL termination** for inspecting the HTTP header or offloading the CPU intensive operation.

![[Pasted image 20260819154608.png]]

Its back-end pools supports **App Services** and **on-premises servers** too unlike load balancer (because pool and balancer has to be in the same vnet). But it can be at most one front-end public and private IP active at a time. It can route to the right pool based on path(/images/ /video/) or domain names if multiple web apps hosted in the same ip address (multiple site, multiple listeners). It can also be configured to show custom error pages.

It has **connection draining** feature which lets you gracefully terminate connections on a instance if you want to do maintanance on it.

These were **regional** solutions so far, they don't balance traffic across regions. The following are the multi-region solutions:

**Global Load Balancer*** uses a single static anycast ip address and acts a global entry point and uses Microsofts global backbone network to direct traffic to closest regional deployment. Works at Layer 4.

**Azure Front Door** uses Microsofts Point of Presences (PoP) with anycast IP addresses and has the capabilities of a Content Delivery Network (CDN) caching to improve performance. It works at Layer 7 only HTTP(S) traffic. Supports TLS/SSL offloading, WAF, fast failover etc. across multiple regions.

**Azure Traffic Manager** uses DNS to distribute traffic to the best fit deployment globally. DNS server responds with the best choice deployments IP. Client will be connected to the instance directly. It can be used for any protocol. It may have some limitations due to some caches not honoring DNS TTL.
