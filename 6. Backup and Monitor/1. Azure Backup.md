
**The Azure Backup** service provides **zero-infrastructure**, secure and cost-effective solutions to back up our data and recover it form the Azure cloud. You can backup on-premises files, folders, system states, Azure VMs, Managed Disks, File Shares, Blobs, Databases, Kubernetees clusters etc. 
![[Pasted image 20260824115235.png]]

For backups no server, infrastructure or storage needs to be deployed by us Azure Backup automatically manages and scales it.

We natively manage our entire backup estate from a central console called **Resiliency** in Azure (formerly Backup Center) enables us to discover, govern, monitor from one unified console. We can use it to manage backups spanning multiple workload types, vaults, subscriptions, regions and Azure Lighthouse tenants.
![[Pasted image 20260824120616.png|286]]

**Recovery Time Objective (RTO)** is the target time within which the business process must be restored after a disaster occurs.
**Recovery Point Objective (RPO)** is the maximum amount of data loss measured in time (Like last 1 hour of stateful data).

For on-premises machines or granular backup of specific files and folders, we can back up directly to Azure with **Microsoft Azure Recovery Services (MARS) agent** (managed inside the guest OS). alternatively we can back up these machines to a backup server, might be a System Center Data Protection Manager (DPM) or Microsoft Azure Backup Server (MABS) and back that server up to Azure. MARS scope is granular file, folder, system state backups and extensions scope is full image-level VM **snapshots**.
If we are using Azure VMs we can install a **backup extension** to back up the entire VM (no agents needed for crash consistent backups for Azure native resources). 
![[Pasted image 20260824190815.png|561]]

These are the **backup types** supported:
- **Full** - The entire thing, initial backup is a full backup.
- **Differential** - Captures only the data that changed since the full backup
- **Multiple backups per day** - We can use **enhanced backup policy** to set backup schedule to 6, 7 etc. hours. unlike older standard backup policy.
- **Selective disk backup** - Selectively back up only a subset of the data disks attached to our VM to reduce cost.
- **Transaction log** - Enables point-in-time restoration up to a specific second.

For backups of Azure VMs all the data transfer happens in Microsoft's backbone network so they don't need internet connectivity (on-premises VMs with MARS agents does need). 

The vault should be in the same region with the data source.

It supports **self-service backup and restores** for application administrators.

It provides in-built job monitoring for operations about backups(configuring, restoring, deleting etc.) via **Workbooks**.

In **Workload integration layer** a **backup extension** specific to each workload is installed. At the time of backup it generates the backup which could be **storage** (snapshots using a VM or Azure Files) or **Stream backup**(For databases like SQL or HANA running in VMs). Then the backup data is transferred to Azure Backup which manages storage by using NSG, firewalls or endpoints.

In **Data Plane** there are three **Access Tiers** where the backup can be stored:
- **Snapshot** - In the first phase of backup the snapshot (VM/Azure Files/Blobs) is taken and stored along with the disk. They are retained in a resource group, it ensures that restores are quick (instant restore) because it is available locally to the customer.
- **Vault-standard** - Backup data for all supported workload is stored in **vaults** (Recovery services vault, Backup vault). It is an online storage tier which holds backup storage and autoscaling set of managed storage accounts. It ensures backup data is available even if the data source is deleted or compromised. 
- **Archive** - For **Long-Term Retention (LTR)** data for compliance rules (short-term would be daily or weekly), it is used for older backup data that is rarely accessed. LTR can be **Planned** (knowing data is required for years in advance), **Unplanned** (when we don't know in advance and do on-demand backup with specific custom retention settings).

In **Data Plane** again there are features for **availability and security**. Backup data is replicated based on the redundancy you specify, might be LRS, ZRS or GRS. **Cross Region Restore (CRR)** allows us to restore backed up data in the paired secondary region from point-in-time recovery points.
It provides built-in security to our backup environment both in transit and rest by encryption (can be with CMK too), RBAC, private endpoints (public network restriction), alerts, soft-delete etc. securing against ransomware, malicious admins, accidental deletions etc.

In **Management Plane** there is **Recovery Services vault/Backup vault and Resiliency in Azure**. It uses these vaults to orchestrate and manage backups, provides an interface for the user to interact with the backup service and is a RBAC boundary. If our backups are spread across multiple subscriptions we can create multiple vaults with one or more vault per subscription. **Protection policies** which covers both **backup policies**(defines when the backups are triggered and how long they are retained) and **replication policies**(Azure Site recovery) is configured here. We need to assign a managed identity to vault for backing up PaaS but not needed for VM. **Recovery Services Vault** is for VMs, Databases in VMs, Azure Files, On-premises servers and site recovery,  **Backup Vault** is for Blobs, Managed Disks, Azure Database for PostgreSQL and AKS. A vault cannot be deleted if it has protected data source, backup data or soft deleted data.

For **Azure Site recovery** the **recovery services vault** must be located in the target region and when you enable it it installs an site recovery extension to the VM and a cache storage account in the source region.
To perform a **test failover** you go to vault, click **replicated items** under protected items, and select VM and click test failover and choose a recovery point and an isolated vnet. It'll seen in **site recovery jobs** and new VM resources will be created (site recovery doesn't keeps idle VMs in target region it replicates the data).
A real **failover** shuts down the source VM and it is deployed to a production VNet. the status of VM is by order Protected, failover pending commit, committed and reprotected. After failover you **commit** to finalize the VMs placement in new region and **Re-protect** to start copying data from secondary region back to primary region for DR.

For VMs the snapshots are "VM Snapshot" for Windows which works with VSS to take copy on both disk and memory and "VM SnapshotLinux" for the Linux.
These are the levels of consistency:
- **Application consistent** - It captures Disks + OS cache (pending writes to disk) + all live database transactions with VSS (for linux you need pre or post scripts to capture app state). 
- **File-System Consistent** - Captures Disks + flushed OS system cache. Installed apps need to do their own cleanup.
- **Crash consistent** - Captures only what was on the disk at the moment.

A scheduled backup can still happen even when the VM is deallocated or stopped as long as disk is still attached to the VM.

These are the ways to restore a VM:
- **Create a new VM** - A new VM is quickly created and runs from a restore point.
- **Restore Disk** - Restores the VM Disk which can be used on a newly created VM which can have different settings from the original.
- **Replace existing** - Replaces a disk on existing VM. Azure takes a snapshot of disk before replacing and stores it in a staging location(storage account) you specify. The current VM must exist.
- **Cross Region**, **Cross Subscription**, **Cross Zonal**
- **Selective Disk**
(check Azure VM Backup restore from docs)

We can also recover individual files from a recovery point by mounting the snapshot using iSCSI initiator.

Backups work for disks which are encrypted with Azure Disk Encryption too
