
**Azure Monitor** helps you track the health, performance etc. and respond to monitoring data of the VM host, OS, workloads and apps with built-in and customizable monitoring abilities. Collects telemetry data from all levels of our cloud and hybrid deployments (Azure Arc).

It has two main monitoring features: **Azure Monitor Metrics** and **Azure Monitor Logs**.
**Metrics** are numerical values collected at predetermined intervals (might be performance, resource utilization, error counts etc.)
**Logs** are recorded system events, it doesn't collects these by default but we can configure Azure Monitor Logs to collect from any resource which then stored in a **Log Analytics workspace** for querying and analysis.

Each of the layers has distinct set of telemetry and monitoring requirements:

**VM host** represents the compute, storage and network resources that Azure allocates to the VM. Azure automatically collects bacis metrics for it like availability, CPU usage etc. will have built-in metrics graph for that under Overview -> Monitoring. **VM host metrics** can be used to trigger an alert when CPU is at a percantage, identify patterns etc.
**Metrics Explorer** allows us to create customized metric charts, you can go there either from Azure Monitor page or under Metrics on resource. It uses Azure Monitor Metrics not logs. These are the options for plotting:
![[Pasted image 20260827114053.png|645]]
You can **Add metric** to plot more than one graph at the same chart.

**Activity Logs** are about **control plane** operations (startup, modification etc.). They are captured automatically. Optionally we can create diagnostic settings to send it to these locations: **Azure Monitor Logs** (complex querying and alerting), **Azure Storage** (cheaper, long-term archiving) and **Azure Event Hubs** (To forward outside of Azure).

When you are creating a VM, under Monitoring you can enable **recommended alert rules**(predefined set of alert rules) to notify us about some occurrences like recommended network usage levels etc.

**Boot diagnostics** are host logs to help us troubleshoot boot issues. We can view serial console log output of the VM boot sequence. Can be enabled under Monitoring and can use a managed storage account to store the data. Can view it under Help -> Boot diagnostics.

Platform/Host data can be optionally sent to a **Log Analytics Workspace** (In Azure Monitor Logs, it is the final destination and storage for data and an analytics engine) with **Diagnostic settings**(usually for PaaS, audit, alllogs) or **Data Collection Rule (DCR)** (supports data transformation, filtering and 1-to-many mapping unlike diagnostics, if we forward them to a storage account or event hub DCR resource needs a managed ID with required roles).

**Log analytics workspace** includes tables (Event, Syslog,  Perf, AzureDiagnostic etc.) that ingests logs and allows for KQL and have **interactive** periods and long-term retention periods. You might search or restore for making long-terms interactive again. Each table has one of the following **table plans** that can be changed and has different ingestion and query costs:
- **Analytics** - Full KQL multi-table joins, real-time alerting etc. has interactive retention 30-90 days.
- **Basic** - Full single Table KQL 30 day interactive. simple log alerts supported.
- **Auxiliary (Lake)** - lowest ingestion cost for compliance scenarios. alerts can be supported indirectly via Summary rules.

For monitoring the software and processes running on our VM, we monitor the **guest**/**client**. It includes the **OS**, **workloads** and **apps**. memory is also guest level since it is managed by kernel.

To enable monitoring in client layer we need to deploy **Azure Monitor Agent (AMA)** to VM, you go to **VM insights** and it redirects you to monitor part and you click **Unlock enhanced monitoring**. You choose a target **Log Analytics Workspace** and leave the **DCR** on the default and it installs the AMA automatically and also has predefined **Workbooks**(are flexible canvases that combine text, queries, metrics and parameters into visual reports). There is also a map feature that visualizes the VMs dependencies.
![[Pasted image 20260827143442.png|512]]

A **DCR** dictates what performance counters and logs are gathered and where they should be sent. If we want to create custom DCR to collect Linux Syslog or something else we'll follow these steps:
1. Go to Monitor page and click create in Data Collection Rules![[Pasted image 20260827155206.png]]
2. You choose the platform type from Basics and then from Resources you add resource (Data Collection Rule Association (DCRA)) with a **Data collection endpoint (DCE)**(provides specific connection strings to move data to Azure Monitor. Is the target connection for the AMA).
   ![[Pasted image 20260827155754.png|454]]
3. From the Collect and deliver you choose what data should be collected from the resources and where they should be sent (LAW and DCR should be in the same region). In our case it is Azure Monitor logs. When it is applied it automatically enables managed identity for VM and tries to install the AMA extension. (but you have to specify it if it is IaC) (for VMs with AMA a managed ID for DCR isn't needed because AMA just pulls the config from it).
   ![[Pasted image 20260827155918.png|465]]

To view log data it collected, you click Logs under monitoring of VM or go straight to the Log analytics workspace for it. There are built-in queries in Kusto Query Language (KQL) also a query window for custom queries
![[Pasted image 20260827161410.png|541]]

By default VMs monitoring agents communicate with Azure Monitor via public endpoints, with **Azure Monitor Private Link Scope (AMPLS)** enabled it connects to it via a **private endpoint**.

An **alert rule** can be triggered by **metrics**, **logs**(runs a saved query against log analytics workspace), **activity logs** or **service health** and based on severity.
When creating an alert rule under Alerts, you choose **scope** and an condition which might look like this for an **automation account** scope:

(one alert rule per signal type)

Then we choose Actions to connect the alert to which might be **action group**, **quick action** or none(alert is only seen in alert history). Then some more details about the alert itself.

An **action group** defines what to do when an alert is triggered might be sending notification to email or an action that runs a **Automation Runbook**. The options look like this:
![[Pasted image 20260828181507.png|608]]

An **alert processing rule** is a tool that changes how fired alerts behave when they are triggered. They act as a central routing for alerts that intercepts them before any notificaitons or actions are triggered. When alert is triggered it chooses if it will trigger an action group or suppress it (Like suppressing an alert if it is at the date of maintanance and trigger action group anytime else, a suppress rule always have higher priority).

**Azure Advisor** continiuously analyzes our cloud to provide personalized optimization guidance for these:
- **Cost** - Helps us optimize and reduce overall spending (right-size or shutting down underutilized VMs, Savings plans, reservations, unused resources etc.)
- **Security** - Identifies vulnerabilities, config gaps (MFA, restricting public access etc.)
- **Reliability** - Improves continuity, uptime (VM backups, Health checks, AZs etc.)
- **Performance** - Improves speed, responsiveness and scale (upgrade storage, autoscaling etc.)
- **Operational Excellence** - Helps us achieve workflow efficiency, manageability and deployment best practices (repair alert rules, azure policy, service health alert etc.)
All recommendations can be found in: Azure Advisor Docs -> Recommendations.
