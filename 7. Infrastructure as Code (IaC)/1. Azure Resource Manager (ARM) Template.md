
It is an **Infrastructure as Code (IaC)** in JSON which allows us to specify our infrastructure in a declarative (opposed to imperative scripts) and reusable way. It can be integrated into CI/CD pipelines
(Bicep is simpler).

It is idempotent, which means you can deploy same config many times without duplicate resources (but it won't let you deploy if you try to change an unchangeable thing). ARM orchestrates it and resources are created in parallel (thats why you might need to specify dependencies with dependsOn or reference and optionally as a child resource). 

By default an ARM template spans a single resource group, by changing deployment scope we can specify governance (policies, locks), access controls (roles) and infrastructure hierarchies (subscriptions, management groups).

In the template, the "schema", "content version", "resources" sections are mandatory.

Deployment "Mode" determines how azure handles existing resources that are not in our template in a scope.
**Incremental Mode (default):** It doesn't removes the missing resources in the scope, if it exists it updates it according to template.
**Complete Mode:** Removes the resource if it doesn't exists in template.

ARM template **parameters** adds flexibility to our template, we don't have to hardcode the parameters and can use the same template for different deployments (different SKUs, names etc..).

In **outputs** section we can specify the values to return after successful deployment.

A template with these and its deployment looks like this:
```
{
	"$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
	"contentVersion": "1.0.0.0",
	
	"parameters": {
		"storageName": {
			"type": "string",
			"minLength": 3,
			"maxLength": 24,
			"metadata": {
				"description": "The name of the Azure storage resource"
			}
		},
	
		"storageSKU": {
			"type": "string",
			"defaultValue": "Standard_LRS",
			"allowedValues": [
				"Standard_LRS",
				"Standard_GRS",
				"Standard_RAGRS",
				"Standard_ZRS",
				"Premium_LRS",
				"Premium_ZRS",
				"Standard_GZRS",
				"Standard_RAGZRS"
				]
		}
	},
	
	"functions": [],
	"variables": {},
	
	"resources": [
		{
			"type": "Microsoft.Storage/storageAccounts",	
			"apiVersion": "2025-01-01",
			"name": "[parameters('storageName')]",
			"tags": {
				"displayName": "[parameters('storageName')]"
			},
			"location": "[resourceGroup().location]",
			"kind": "StorageV2",
			"sku": {
				"name": "[parameters('storageSKU')]"
			}
		}
	],
	
	"outputs": {
		"storageEndpoint": {
			"type": "object",
			"value": "[reference(parameters('storageName')).primaryEndpoints]"
		}
	}
}
```

With **Azure CLI** we pass the parameters with the flag "--parameters" and list them like storageName="thisissouniquedawg" storageSKU="Standard_LRS".

Optionally you may pass the parameters with a .json **parameter file** with the flag "-TemplateParameterFile". and for CLI you do "--parameters ./param_file.json".

**Variables** are useful when there is long expressions you use a multiple times in the file.

A **copy** element can be added to create multiple resources, properties and variables depending on where you put it. If we were to create three storage accounts, under the resource we'll add something like
```
	"copy": {
        "name": "storageCopy",
        "count": 3
    },
```

**Condition** property is used when we want to evaluate an expression and decide whether to deploy resource or not based on that. something like this under the resource:
```
"condition": "[equals(parameters('newOrExisting'),'new')]",
```

We can **nest** templates or **link** them with a uri to modularize them
