
An **identity** is a set of information that uniquely describes a user, device or application. When a user presents an identity, it is **who they claim to be***.

A **security principal** is the actual entity inside the system, when a user proves their identity, the system looks up their security principal and attaches permissions directly to this principal.

In Entra ID, a user account contains all the information needed to authenticate the user, once authenticated Entra ID builds an **access token** to authorize the user. You manage the user objects usually in **Microsoft Entra admin center** or **Azure Portal** (you can work with one directory at a time).

A **user principal name (UPN)**  is a unique login name for a user that looks like an email address (shows like agea@bruhcompany.onmicrosoft.com if you didn't configure custom domain name, .onmicrosoft one exists in background either way).

**User Type** column shows either **member** or **guest** but Entra ID defines users in three ways:
- **Cloud identities** - Only exists in Entra ID, the source is cloud (in this directory or another Entra ID directory.)
- **Directory-synchronized identities** - Exists in an on-premises AD, something like **Entra Cloud Sync** or **Entra Connect Sync** brings them to Entra ID, the source is Windows Server AD
- **Guest Users** - Exists outside our organization, might be from other cloud providers and Microsoft accounts, the source is **Invited user**.

When you delete a user the account is suspended state for 30 days, you may restore the account with all of its properties from the **deleted users** during that time, after that it is deleted, or you may permanently delete at the same place.
At least one of the roles is required for deleting or restoring users: Global administrator, Partner Tier-1 Support, Partner Tier-2 Support, User administrator.

An **Entra group** helps organize users, which make it easier to manage permissions (for role assignable groups you need at least P1 license). Entra ID has two different kinds of groups:
- **Security groups** - Are used to manage access to resources, can include users, devices and service principals.
- **Microsoft 365 groups** - Provides collaboration by giving members shared mailbox, calendar, files, SharePoint site and more.

![[Pasted image 20260726144408.png]]

Another characteristic of a group is the **Membership Type**, specifies how members are added to the group:
- **Assigned**: - Members are added and maintained manually.
- **Dynamic User** - Users are added and removed automatically based on rules on user attributes(properties) like department, location etc. (requires at least Entra ID P1 license).
- **Dynamic Device** - Devices are added and removed automatically based on rules on device attributes (only security groups, Microsoft 365 groups doesn't supports it).

**Device Identities** helps to ensure standards for security and compliance are met with tools like **Microsoft Intune**.

![[Pasted image 20260726150253.png]]

There are different join types for devices:
- **AD joined** - Bound to an on-premise domain controller, uses local domain credentials and controlled via local GPOs and traditional tools, they won't be seen in Entra all devices.
- **Entra registered** - Provides support for BYOD or mobile device. You sign into device with your local account (like a Microsoft Account). Registered when you sign in with a organizational account to a resource(like SharePoint or Teams). Provides SSO to cloud resources and Conditional Access if enrolled in Intune. Optionally **Mobile Device Management (MDM)** can be used.
- **Entra Joined** - Used when cloud-first is wanted. You sign into the device with a organizational account. Provides MDM, SSO, Conditional Access, Self-service password reset and Windows Hello PIN reset.
- **Hybrid Entra joined** - Suitable for hybrid organizations with existing on-premises and cloud infrastructure. Devices are joined to AD and registered with Entra directory. Provides SSO both cloud and on-premise resources and everything an Entra joined device has.
**Cloud Kerberos Trust** allows Entra joined and Hybrid joined devices to authenticate to on-premises resources (SSO) without device objects having to be written back to on-premises AD.

Microsoft's paid cloud **service**s (like Microsoft 365, Enterprise Mobility + Security, Dynamics 365) require **license**s. Adding, removing, reprocessing licenses are managed with **Microsoft 365 admin center** or **PowerShell** and **Microsoft Graph API**. 

It provides **group-based licensing**.  You can assign one or more licenses to a **security group**(can be synced too) now you don't need a complex PowerShell script to automate license assignments when a user joins or leaves a department (it requires at least P1 license). 
Some service plans in a product license can be disabled if company sees fit.
If a user has a license assigned both directly and by group it takes effect once.

In group-based licensing a user might be in a **licensing error state** and errors are recorded in user object, if it was a direct assignment it'd be immediately reported back. (**directly** vs **inherited**)
Some common errors and how to solve them are:
- **CountViolation** - You don't have enough licenses, can see how many licenses you have in Billing section of both centers, just buy more or free up unused ones.
- **MutuallyExclusiveViolation** - A product contains a service plan that conflicts with another that's already assigned (like SharePoint Online plan 1 or 2 in Office 365 Enterprise E1 and E3). You have to remove one of them to fix.
- **DependencyViolation** - Happens when they try to remove a product that contains a service plan that must be enabled for another service plan to function. You have to make sure required plan is assigned by some other method, after that you can remove it from the group.
- **ProhibitedInUsageLocationViolation** - Some services aren't available in all locations. **Usage Location** property(attribute) of the user must be specified. if users location isn't allowed just just remove it from the group.
- **LicenseAssignmentAttributeConcurrencyException** - It is a concurrency thing, you don't gotta do anything it'll retry it.

![[Pasted image 20260726162505.png]]

Keep in mind:
- For one user in group, if multiple products in group, and one of them fails for that user, other license for that user won't be assigned either, its all or nothing.
- You must remove all licenses assigned to the group before you can delete the security group.
- You might have to manually trigger **Reprocess** for assignments after you resolve a problem.
- With groups temporary co-existence is allowed with conflicting ones while changing assignments without losing service (Like moving from E1 to E3 by groups)

**Automatic user creation** is achieved by connecting HR systems and Entra ID, it creates and deletes users automatically by pulling data from Human Capital Management (HCM) systems. (from sources like Workday, SAP etc.)
It uses SCIM or API-driven inbound provisioning.
